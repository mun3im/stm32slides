\begin{frame}{Why This Chapter Matters}
    \begin{columns}[c]
    \begin{column}{.47\textwidth}
        {\normalsize Your gate circuits did only what their \alert{wiring} told them. To change the behaviour, you had to rewire. A microcontroller is a digital circuit too, but a \alert{program stored in memory} controls it. The same silicon can blink an LED, measure a temperature, or drive a motor. It depends only on the bits you load.}
    \end{column}
    \begin{column}{.51\textwidth}
        \begin{block}{After this chapter, you can:}
        {\small
        \begin{enumerate}\itemsep2pt
            \item Define an embedded system and its design constraints.
            \item Distinguish a \alert{microprocessor} from a \alert{microcontroller}.
            \item Name the CPU functional units and the role of each.
            \item Explain the address, data and control buses, and compute addressable memory.
            \item Trace a short program through fetch--decode--execute.
            \item Describe how one C statement changes a voltage on a pin.
        \end{enumerate}}
        \end{block}
    \end{column}
    \end{columns}
\end{frame}

\begin{frame}{The One Question}
    \leavevmode
    This chapter introduces many new terms. Every section answers just
    one question. This question is the \alert{thread} that connects
    everything that follows:

    \vspace{4mm}
    \begin{center}
    \fbox{\parbox{.78\textwidth}{\centering\vspace{2mm}
    \large How does a program cause hardware to do something?
    \vspace{2mm}}}
    \end{center}

    \vspace{4mm}
    \begin{block}{The one fact to carry out of this chapter}
        \alert{The CPU has no special instruction for ``turn on an LED''.}

        \vspace{2mm}
        It only has instructions that \alert{read and write memory
        addresses}. Some of these addresses connect not to memory,
        but to hardware instead.

        \vspace{2mm}
        So turning on an LED means \alert{writing a number to an
        address}.
    \end{block}
\end{frame}

\begin{frame}{What Makes a System Embedded}
    \leavevmode
    {\small Every machine on the last slide is still just a computer:
    processor, memory, I/O. The difference is \alert{what the
    processor is for}. A general-purpose computer is built to run
    whatever the user installs next. An embedded system is built into
    a product to perform one job.}

    \vspace{2mm}
    \begin{columns}[T]
    \begin{column}{.48\textwidth}
        \textbf{General-purpose computer}
        \begin{itemize}
            \item Runs many different applications
            \item End-user installs new software freely
            \item \alert{Faster is always better}
            \item Sold on speed, compatibility, price
        \end{itemize}
    \end{column}
    \begin{column}{.48\textwidth}
        \textbf{Embedded system}
        \begin{itemize}
            \item Runs a few functions, fixed at design time
            \item Firmware is written once, by the designer
            \item Must meet a \alert{fixed deadline}; extra speed may not help
            \item Sold on power, cost, size, \alert{predictability}
        \end{itemize}
    \end{column}
    \end{columns}

    \vspace{3mm}
    \begin{block}{The idea that matters}
        A desktop that answers in 100\,ms instead of 10\,ms is just
        slow. But an airbag controller that fires in 100\,ms instead
        of 10\,ms has \alert{failed}.

        \vspace{1mm}
        Embedded engineering cares about \emph{predictable} time, not
        maximum speed.
    \end{block}
\end{frame}

\section{Inside the Computer}

\begin{frame}{Microprocessor and Microcontroller}
	\leavevmode
	{\small SWaP-C is a design constraint. Integrating the processor,
		memory, and peripherals onto \alert{one chip} is how that
		constraint gets met in practice: fewer parts, smaller board,
		lower cost per unit. This single-chip design is called a
		\textbf{microcontroller}.}

	\vspace{2mm}
	\begin{center}
		{\small
			\striped
			\begin{tabular}{@{}l l l@{}}
				\toprule
				\textbf{Feature} & \textbf{Microprocessor ($\mu$P)} & \textbf{Microcontroller ($\mu$C)} \\
				\midrule
				Integration  & Processor chip only & Processor, RAM, ROM, I/O on one die \\
				Flexibility  & Memory and peripherals scale & Resources fixed inside the chip \\
				Complexity   & Many components, complex PCB & Few components, simple board \\
				Power, cost  & Higher & Optimised for low power and unit cost \\
				Performance  & High clock, heavy computation & Lower clock, control and I/O \\
				\bottomrule
		\end{tabular}}
	\end{center}

	\vspace{3mm}
	\begin{block}{A microprocessor needs help; a microcontroller comes ready}
		A microprocessor generally has no RAM, no ROM, and no way to
		reach the outside world on-chip; those parts must be wired
		around it before it can do anything. A microcontroller puts
		all of this together on one chip. \alert{The Nucleo's chip is
			a microcontroller}: everything on the earlier board slide
		sits inside one package.
	\end{block}

\end{frame}

\begin{frame}{Memory: ROM and RAM}
    \begin{columns}[T]
    \begin{column}{.48\textwidth}
        \textbf{ROM --- non-volatile}
        \begin{itemize}\itemsep1pt
            \item Contents survive with \alert{no power}
            \item Holds the program: fixed at manufacture, or
                  ``burned'' with a programmer
            \item \textbf{Flash} is the dominant type: NAND or NOR
            \item STM32 devices use \alert{NOR flash} for code
        \end{itemize}
    \end{column}
    \begin{column}{.48\textwidth}
        \textbf{RAM --- volatile}
        \begin{itemize}\itemsep1pt
            \item Contents \alert{lost} without power
            \item Holds temporary data: variables, the stack
            \item \textbf{SRAM}: fast, every embedded system has it
            \item \textbf{DRAM}: cheaper, needs refresh; only larger
                  systems bother
        \end{itemize}
    \end{column}
    \end{columns}

    \vspace{3mm}
    \begin{block}{On the Nucleo-F446RE}
        \textbf{512\,KB Flash} holds your program. \textbf{128\,KB
        SRAM} holds your variables and stack. Chapter~3 returns to
        this split in detail.
    \end{block}
\end{frame}

\begin{frame}{Machine Code and Assembly Language}
    \leavevmode
    {\small Step 1 of fetch--decode--execute reads a ``machine code
    instruction.'' What is that, really?}

    \vspace{2mm}
    \begin{columns}[T]
    \begin{column}{.48\textwidth}
        \begin{block}{Machine language}
            {\small The lowest level. A bit pattern, such as
            \texttt{0001 1011}, that the Decoder is built to
            interpret. This is the \alert{only} language the CPU
            itself understands.}
        \end{block}
    \end{column}
    \begin{column}{.48\textwidth}
        \begin{block}{Assembly language}
            {\small A human-readable \alert{mnemonic} per
            instruction --- \texttt{MOV}, \texttt{ADD}, \texttt{MUL}
            --- translated to machine code by an \textbf{assembler}.
            One line in, one instruction out.}
        \end{block}
    \end{column}
    \end{columns}

    \vspace{3mm}
    {\small A \textbf{cross assembler} runs on one computer (your PC)
    and generates machine code for a different one (the Cortex-M4)
    --- the normal situation in embedded development.}

    \vspace{2mm}
    {\small Chapter 5 returns to assembly language in depth, once the
    Cortex-M4's own registers and instructions are in place.}
\end{frame}

\begin{frame}{The Three Buses}

\begin{center} \begin{tikzpicture}[ >=Stealth, bus/.style={thick}, block/.style={draw, rounded corners, minimum width=2.5cm, minimum height=14mm, fill=blue!10} ] \node[block] (cpu) {CPU}; \node[block, right=5cm of cpu] (mem) {Memory / I/O};
		% Address bus
		\draw[->, red, bus] ([yshift=10pt]cpu.east) -- node[above] {\scriptsize Address Bus} ([yshift=10pt]mem.west);
		% Data bus
		\draw[<->, blue, bus] (cpu.east) -- node[above] {\scriptsize Data Bus} (mem.west);
		% Control bus
		\draw[<->, green!60!black, bus] ([yshift=-10pt]cpu.east) -- node[above] {\scriptsize Control Bus} ([yshift=-10pt]mem.west); \end{tikzpicture} \end{center}
    \begin{center}
    {\small
    \striped
    \begin{tabular}{@{}l l l@{}}
        \toprule
        \textbf{Bus} & \textbf{Direction} & \textbf{Carries} \\
        \midrule
        \textbf{Address} & Unidirectional, CPU $\rightarrow$ device
            & \emph{Which} location. Width sets the addressable range \\
        \textbf{Data}    & Bidirectional
            & \emph{What} value. Width sets how much moves per transfer \\
        \textbf{Control} & Bidirectional
            & \emph{When} and \emph{what kind}: read/write, timing, interrupts \\
        \bottomrule
    \end{tabular}}
    \end{center}

    \vspace{3mm}
    \begin{block}{Address width sets the memory map}
        $2^{n}$ addressable bytes for an $n$-bit address bus.

        \vspace{1mm}
        $2^{16} = 64$\,KB \quad$\cdot$\quad $2^{20} = 1$\,MB \quad$\cdot$\quad
        $2^{32} = \alert{4\,\text{GB}}$: the Cortex-M4
    \end{block}

    \vspace{2mm}
    {\small \textbf{You already know this:} an address is the input
    to a \alert{decoder}. It works the same way as the one-of-$N$
    selection you built with a 3-to-8 decoder, just at a much larger
    scale.}

\end{frame}


\begin{frame}{Using the Buses: Fetching an Instruction}
    \leavevmode
    Suppose the CPU needs the instruction stored at \texttt{0x1000}:

    \vspace{2mm}
    \begin{center}
    {\small
    \begin{tabular}{@{}l l@{}}
        \toprule
        \textbf{Bus} & \textbf{Carries, this step} \\
        \midrule
        Address bus & \texttt{0x1000} --- CPU asks for this location \\
        Control bus & \texttt{READ} --- CPU asserts a read \\
        Memory      & responds with \texttt{LOAD 0x2000} \\
        Data bus    & carries that instruction back to the CPU \\
        \bottomrule
    \end{tabular}}
    \end{center}
\begin{center} \begin{tikzpicture}[ >=Stealth, block/.style={draw, rounded corners, minimum width=2.8cm, minimum height=1.6cm} ] \node[block, fill=blue!10] (cpu) {CPU}; \node[block, fill=orange!10, right=5cm of cpu] (ram) {RAM}; \draw[->, very thick, red] ([yshift=14pt]cpu.east) -- node[above] {\small Address: 0x1000} ([yshift=14pt]ram.west); \draw[<->, very thick, blue] (cpu.east) -- node[above] {\small Data: "LOAD 0x2000" instruction} (ram.west); \draw[<->, very thick, green!60!black] ([yshift=-14pt]cpu.east) -- node[above] {\small Control: READ} ([yshift=-14pt]ram.west); \end{tikzpicture} \end{center}
    \vspace{1mm}
    \begin{block}{The same pattern repeats for every data access}
        The address bus names the location. The control bus says read
        or write. The data bus carries the value. \alert{Three buses,
        one transaction.} We will use this exact pattern again when we
        trace a program.
    \end{block}
\end{frame}


\begin{frame}{Memory-Mapped I/O}
    \leavevmode
    {\small The CPU talks to peripherals the \alert{same way} it
    talks to memory: same address bus, same data bus, same read/write
    control line.}

    \vspace{2mm}
    \begin{center}
    \begin{tikzpicture}[x=9mm, y=7mm]
        \node[cpublk, minimum width=20mm, minimum height=10mm] (cpu)  at (0,0)   {CPU};
        \node[memblk, minimum width=26mm, minimum height=7.5mm]  (ram)  at (5.4,1.4)  {RAM};
        \node[blk,    minimum width=26mm, minimum height=7.5mm]  (gpio) at (5.4,-1.4) {GPIO peripheral};

        % one shared trunk off the CPU, forking up to RAM and down to GPIO
        \coordinate (trunk) at ([xshift=7mm]cpu.east);
        \draw[busline] (cpu.east) -- (trunk);
        \draw[flow] (trunk) |- (ram.west);
        \draw[flow] (trunk) |- (gpio.west);
        \node[lbl, anchor=south] at ([yshift=1mm]trunk) {\scriptsize address / data / control};
    \end{tikzpicture}
    \end{center}

    \vspace{2mm}
    \begin{block}{How it works}
        {\small
        \begin{itemize}\itemsep0pt
            \item Each peripheral register gets an address in the
                  memory map.
            \item A read or write to that address reaches the
                  register, not RAM --- the peripheral answers.
        \end{itemize}}
    \end{block}

    \vspace{1mm}
    {\footnotesize \alert{Key idea:} ordinary \texttt{LDR}/\texttt{STR}
    reach a peripheral register --- the address alone decides who
    responds.}
\end{frame}

        \texttt{LDR} and \texttt{STR}: \texttt{LDR} the operands in,

        out. Chapters 5--7 explain this idea in more detail.
    \end{block}

\begin{frame}{We Can Now Answer the Question We Started With}
	\leavevmode
	\begin{center}
		\fbox{\parbox{.7\textwidth}{\centering\vspace{2mm}
				\large How does a program cause hardware to do something?
				\vspace{2mm}}}
	\end{center}

	\vspace{3mm}
	{\small We just traced \texttt{z = x + y;} through LOAD, ADD, and
		STORE --- ordinary memory addresses, nothing more. But the
		\alert{same} load/store mechanism works on any address. Give it
		the address of a peripheral register instead of a memory cell,
		and it changes hardware, not a variable.}

\begin{frame}[fragile]{One Line of C, Back on the Board}
	\begin{columns}[c]
		\begin{column}{.46\textwidth}
			Look at this line. It appears in almost every STM32 program ever
			written:

			\vspace{2mm}
			\begin{lstlisting}[language=C, basicstyle=\ttfamily\normalsize]
	GPIOA->ODR |= (1U << 5);
			\end{lstlisting}

			\vspace{2mm}
			{\small You already know every symbol here: a pointer, a
				structure member, a compound bitwise-OR assignment, and a
				left shift.}

			\vspace{2mm}
			{\small What may not be obvious is that running this one
				statement \alert{turns on an LED}: the LED on \texttt{PA5},
				on the board you met at the start of this chapter.}
		\end{column}

\begin{frame}{The Bookend}
	\leavevmode
	\begin{block}{The CPU still does not know what an LED is}
		It only executes instructions and accesses addresses. Every
		step was ordinary: the same \texttt{LDR}/\texttt{ORR}/\texttt{STR}
		pattern as any other read-modify-write.
	\end{block}

	\vspace{4mm}
	\begin{center}
		\fbox{\parbox{.78\textwidth}{\centering\vspace{2mm}
				\large Turning on an LED is writing a number to an address.
				\vspace{2mm}}}
	\end{center}

	\vspace{2mm}
	{\small You asked this at the start of the chapter, as an
		unexplained claim. Now you can derive it: from a C statement, to
		a register write, to a voltage on a physical pin.}
\end{frame}
